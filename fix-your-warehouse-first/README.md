# fix-your-warehouse-first

An AI assistant pointed at a warehouse with one missing filter reports 2023
revenue as EUR 276,072.90. The true figure is EUR 228,611.75. Nothing errors,
nothing warns, and the number arrives with two decimal places and a tidy
regional breakdown. The assistant is not at fault: its SQL is correct in both
runs, and the only thing that changes between them is one line in one model.

That is the business case for data discipline stated as cheaply as I can state
it. "AI-readiness" is mostly the ability to say what your numbers are worth
before anyone builds a chat interface on top of them. This demo builds the
same warehouse twice, runs nine dbt data tests against each, and asks both the
same question.

## Quickstart

```bash
./verify.sh          # ~1 min: installs dbt into a local venv, then proves both rounds
```

Python 3.12. No API key, no network data, no accounts. `verify.sh` is the
whole contract: it exits 0 only if the broken warehouse is caught by its own
tests and the fixed one answers to the cent.

The bug, in full, is the presence or absence of the `where is_current` line in
`warehouse/models/marts/dim_customers.sql`:

```sql
select
    customer_id,
    region,
    valid_from
from {{ ref('stg_customers') }}
{% if var('scenario') == 'fixed' %}
where is_current
{% endif %}
```

The CRM exports one row per customer *version*. Nine of sixty customers have
moved region at some point, so the dimension holds 70 rows for 60 customers.
`fct_revenue` joins to it on `customer_id`, which is correct code against an
incorrect table, and 83 orders get counted twice.

## What it proves

| Claim | Where |
|---|---|
| A warehouse can be wrong by 20.76% and look completely healthy | `e2e.py` round 1 |
| Ordinary dbt tests catch it: 3 of 9 fail | `warehouse/models/marts/schema.yml` |
| The reconciliation test is the one that names the money | `warehouse/tests/assert_revenue_reconciles.sql` |
| The same assistant answers to the cent once the filter is back | `e2e.py` round 2 |
| A red warehouse is never queried at all | `src/gate.py`, `tests/test_gate.py` |
| The per-region error is not a constant (+11.98% to +32.34%) | `RESULTS.md` |

Measured output, including limitations and what this demo does *not* show, is
in [RESULTS.md](RESULTS.md).

## Layout

```
warehouse/            a real dbt project (dbt-core + DuckDB, builds in seconds)
  models/staging/     typed source views
  models/marts/       dim_customers (the bug lives here), fct_revenue
  models/marts/schema.yml       unique / not_null / relationships / accepted_values
  tests/assert_revenue_reconciles.sql   the lineage test: money survives the joins
  seeds/              synthetic CSVs, regenerate with tools/generate_seeds.py
src/warehouse.py      run dbt, parse target/run_results.json into a test report
src/assistant.py      question to SQL, plus the read-only check on the result
src/gate.py           four lines: no green warehouse, no answer
e2e.py                the end-to-end story, both rounds
```

Two details worth stealing for real systems. A missing `run_results.json`
raises rather than reading as a pass, and a report of zero tests is not green
either — a suite whose selector matches nothing is the most common way a
pipeline reports healthy while checking nothing. Both are in
`tests/test_warehouse.py`.

The question-to-SQL step is a deterministic mapper rather than a model call,
on purpose. It makes the assistant provably correct so that the warehouse is
the only variable. A real model in that slot adds its own error rate on top of
this one; it does not subtract.
